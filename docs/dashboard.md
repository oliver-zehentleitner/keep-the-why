# Dashboard

`keep-the-why-dashboard` is a read-only viewer over what a Keep the Why project already has: the entries in `context/`, the config in `.keep-the-why`, the linter's findings, and the Git history of all of it — who created each entry, who last touched it, when its `Status` changed and by whom.

It connects data that is already lying around. It writes nothing into any project, runs no daemon beyond the terminal you start it in, and is never a source of truth: delete it and nothing is lost. The one file it keeps is `~/.keep-the-why/projects.json`: where the projects you opened live on this machine, shared with the skill's own setup check, so the project menu can offer them again (a `dashboard-history.json` from before 0.2.0 is folded in and removed). That is what keeps it inside this project's own rule — [no new platform, database, daemon, account, or workflow](philosophy.md) — a lens on Markdown and Git, not a place where anything lives.

## Family, friends, thoughts

Three ways projects and entries connect, from close to loose — each one read from what the entries already say, none of them written by the dashboard.

**Family** — projects that belong together. A parent lists its children in its `.keep-the-why`, one scope line each, and each child names its parent; that list is the routing: the agent writes an entry into the member whose scope fits ([Setup, "Family"](setup.md#family-routing-and-writing-across-projects)). The dashboard can show a family as one: with the *family* scope every view — overview, topics, queues, search, the graph — covers the whole tree, and the **Family** view shows its shape.

**Friends** — repositories outside the family that entries here cite, with a `See` or `Superseded by` line naming the other repository's `canonical` and an entry's `Id`. Nothing is routed between friends; they are only linked. The graph draws each friend as a hub with the entries that connect to this project — a friend that is part of a family comes as its whole family, one unit like a repository. One hop: a friend's own friends are not loaded. Click a friend's name to walk there and look one hop from it; the page keeps the *path* you walked, so a web of projects is read from centre to centre. The **Friends** view lists them, with what cites what in both directions.

**Thoughts** — chains of linked entries: each one cites the one before (`See`) or replaced it (`Superseded by`), across projects wherever the graph reaches. Nobody writes a thought; the recorded citations are one. Beside the graph they are listed and light up when pointed at, *read ›* shows a whole thought in one view, and an entry shows the thoughts it is a step of. The **Thoughts** view adds what the lines have in common — where many lead, where many start, the entries many pass through — and where they need a second look: a chain that starts from an entry nobody confirmed, or passes a step in question, with the entries linked after it (a link says related — often follows from, not always), when a line grew. A chain that goes on into a repository the page has not loaded is marked, and one click follows it there.

## Run it

```bash
pip install keep-the-why-dashboard
ktw-dashboard            # in a project with a .keep-the-why file
```

The page opens at `http://127.0.0.1:8765/` and stays current: the server checks the project's fingerprint (HEAD, `.git/index` and `.git/HEAD`, `.mailmap`, `.keep-the-why`, `AGENTS.md`, the files under `context/`) every two seconds and pushes a fresh state to every open page when something changed — after a `git pull` as much as after an agent wrote an entry a moment ago. Uncommitted entries show as author `working tree`, which makes the page a live window on what the skill is capturing during a session.

```
ktw-dashboard [PATH] [--host 127.0.0.1] [--port 8765] [--no-browser] [--interval 2]
              [--scan DIR] [--no-history] [--no-update-check] [--export DIR] [--anonymize] [--json] [--version]
```

| Flag | Effect |
|---|---|
| `--export DIR` | writes `DIR/index.html`, one self-contained page with the state embedded (no server; nothing loaded from elsewhere when it opens — the page asks other hosts only for what a person opens — another project's published `.keep-the-why` and `state.json` when an entry with a reference into that repository is shown, the family scope is chosen, the Family view is opened, an entry Id this export does not hold is opened, a graph is shown with *friends* on (the default), or public mode is on, and a host's API for one commit on a click on an author's name), plus `DIR/state.json` and two live badges, `DIR/badge-entries.svg` (Keep the Why's style) and `DIR/badge-entries-flat.svg` (flat) — static SVG with the project's numbers, "42 entries · 3 open", for the README to link to this export, no badge service in between; then exits. For GitHub Pages, a release asset, or the link behind the [live badge](badge.md#live-badge) |
| `--json` | prints the state and exits |
| `--anonymize` | Git author names become `author-1`, `author-2`, … — for exports of repositories whose contributors did not ask to be listed on a web page. E-mail addresses are never part of the state |
| `--scan DIR` | also look for projects under `DIR` (two levels deep) for the project menu; the parent of the start directory is always scanned |
| `--no-history` | neither read nor update `~/.keep-the-why/projects.json` (where projects have been seen; the skill keeps the same file) |
| `--no-update-check` | don't ask pypi.org for newer versions of the dashboard and the linter — the check runs at start and once every 24 hours and is the server's only network call; a found update makes the package's entry in the status bar shimmer, with the version and the `pip install -U` line in its tooltip. The exported page never checks |
| `--host 0.0.0.0` | exposes the page on the network; the CLI warns. Everything shown is the project's `context/` — treat the port like the repository |

## Show a proposal before it is merged

A `context/` that exists only in a pull request — a retrospective pass for a project that never had one, or a migration — can be shown rendered before the maintainer merges or installs anything: export the page from the branch and publish the export on the fork's own GitHub Pages.

```bash
git checkout <the branch>                                     # in the fork's checkout
ktw-dashboard --export out --anonymize --no-browser --no-history --no-update-check .
```

Publish `out/` as the fork's `gh-pages` branch — an orphan branch holding the four exported files and an empty `.nojekyll` — and switch Pages on once for that branch (`gh api -X POST repos/<owner>/<repo>/pages -f build_type=legacy -f "source[branch]=gh-pages" -f "source[path]=/"`, or the repository's settings). A minute later `https://<owner>.github.io/<repo>/` shows the whole page: overview, graph with every `See` line, friends where the branch cites other repositories, the queues — from one static file, nothing installed, nothing cloned, nothing merged. Link it from the pull request.

Three things to know. The page is a snapshot of the branch: re-export and push `gh-pages` again after the pull request changes. `--anonymize` because it is someone else's repository — the contributors did not ask to be listed on a page of yours. And a `See` line *into* the branch from another project resolves only once the branch is merged (the other page reads the repository's published export at `HEAD`), while the branch's own `See` lines *out* to projects that publish their export resolve right away — a proposal that cites a friend already shows the friendship, the friend shows it back after the merge.

First used for [tarasko/picows#111](https://github.com/tarasko/picows/pull/111), rendered at [oliver-zehentleitner-aigent.github.io/picows](https://oliver-zehentleitner-aigent.github.io/picows/).

## Several projects

Started inside a project, the dashboard shows that one. The project menu shows families grouped — a parent, its children indented below it — and each project's type, repository or cache; the **Projects** view is the same list with the details and the *forget* control. The project menu in the top bar lists the ten most recently opened projects (one project id can appear at several paths — clones, worktrees), projects found near the start directory, and ids that have a personal file in `~/.keep-the-why/` but no known location yet; opening a project moves it to the top of the history.

## What it shows

| View | Content |
|---|---|
| **Strip** (every view) | entries, topics, authors · what needs a person: open, needs review, pending confirmation, unknown evidence, revisit-when triggers · linter errors and warnings — each a link |
| **Overview** | Type / Status / Evidence distributions, config (and the personal defaults the project offers), topic cards, recently touched entries; with the *family* scope a banner naming the members |
| **Graph** | topics as hubs, entries around them colored by Evidence — a ring marks `open` / `needs-review` / `pending-confirmation`, a hollow dot `superseded` — and references between topics as edges, plus every `See` and `Superseded by` between two entries, found by Id (drawn between their topics while entries are hidden). Drag, zoom, hover to focus a neighbourhood, click to open. With the *family* scope (the switch next to the project menu, below) it is the family graph: every project of the tree as a hub in its own colour with its topics around it, parent and child projects joined by a thick dashed line, and every `See` and `Superseded by` between two entries drawn as a line — across projects too, and between their topics while entries are hidden. A member that is not available is named in the legend, not left out silently. **Friends:** the repositories the graph's entries cite by a cross-project `See` or `Superseded by` outside the family (with the *project* scope the declared parent and children count as family, on the live server the whole tree). They load as soon as a graph shows them, in every mode, the way a reference row resolves them (a project known to the live server, else the repository's published export), one level deep; unchecking *friends* in the graph turns that off for this browser, and *friends (N)* then loads them on a click. *all their entries* shows every entry of every friend, not only what links here (off by default, kept per browser). Each friend is a hub with a dashed ring showing the entries cited there, joined by their `See` lines; a friend that is part of a family comes as the whole family — one unit, like a repository: a hub per member, joined by their parent lines; a click on the hub shows all of it, the name in the legend opens that project's own graph — the reader moves the centre there and sees one hop from it. The side pane's graph has the same *friends* control in its corner; in its *near* view the control switches to the project level (the family level with the family scope) and loads them there. **Thoughts:** beside the graph, the chains of linked entries in it — the longest chains of `See` and `Superseded by` between entries, each one citing the one before (a `See` runs from the later entry to the earlier, a `Superseded by` from the old entry to its successor), from 3, 4 (the default) or 5 entries up, across projects where the graph spans them. Pointing at one lights its path, a click holds it and lists its steps, origin first; a chain made only of `Superseded by` is marked *evolution*. *read ›* opens the whole thought in one view (`#thought/<id>,<id>,…`): every entry in order and in full, joined by how each follows from the one before. A friend or a step of the path shows not only the entries cited there but everything its own `See` and `Superseded by` chains connect to them, so a thought runs through it whole. A chain that goes on into a repository the page has not loaded — a `See` from its origin, or a `Superseded by` naming a successor there — says *continues ↗ owner/repo*; shorter chains like that are listed under *Going on beyond this page*. *load the whole chains* (or a single chain's *continues*, or *load the whole chain* in the reader) loads exactly the repositories on the chain, each as a unit, hop by hop until it ends — up to eight hops, nothing else of theirs; they are drawn like friends and marked *via a thought*. What cites a chain's newest entry from a repository that is not loaded cannot be known — there is no index of the web. An entry that is a step of a thought lists it beside its backlinks, with its place (*step 2 of 5*). In the graph the projects of one unit — a family, a friend's family — keep together, and different units keep their distance. **Path:** going to a friend — its name in the legend, one of its entries, any link to it on the page — moves the page's centre in place, without a reload, and the project left joins the *path*: a bar above every view (an overlay on the graph) names the projects walked through, each a way back that shortens it, and the graph shows them as numbered hubs with a dotted ring, joined in the order walked, with the entries that link them. Back and forward walk it; *discard* clears it, *in graph* hides it, *path* in the graph turns keeping it off (on by default, kept per browser). A reload or a link opened anew starts without a path — a link leads to an entry. **Project names:** the name under a project's hub is always shown, whatever *labels* says, and it is a link — to a friend's graph (in place, keeping the path), back to a step of the path, or to a family member's graph; a click on the hub itself expands a friend. **Motion:** the graph turns very slowly in its plane, one turn in about six minutes; it stops while pointed at or dragged, stays still with the system's reduced-motion setting, and *motion* in the graph turns it off (kept per browser). Friends are linked, never merged: search, queues, counts and the other views stay with the project or the family. A friend that cannot be loaded is named in the legend with the reason |
| **Topics** and the reader | one topic file with its entries; an entry rendered with its fields, `Reason` / `Rejected alternative` / `Consequence` as callouts, references as links, previous / next |
| **Details pane** | for the open entry: fields, created by / last touched / status history from Git, backlinks (entries elsewhere that reference this file), linter findings on this entry. Its graph has a switch in the corner — *near* (the entry's or topic's neighbourhood, including every entry it points at or that points at it by `See` or `Superseded by`), *project*, and *family* where the family scope is available. It starts with the page: *near* on an entry or a topic, otherwise the scope next to the project menu, so with *family* the overview shows the family graph; a click in the corner holds until the scope changes. Beside the backlinks: the thoughts the entry is a step of (with its place in each), and for an entry in question the later entries linked after it. The pane's width is chosen at its top — 1×, 2× (the default), 3×, or half the page. *⤢ full graph* in the corner of its graph opens the full graph at the same level, centred on the entry or topic shown |
| **Queues** | what needs a person: `Status: open`, `needs-review`, `pending-confirmation`, `Evidence: unknown` on every entry still in force — an open question with an untraced origin counts there too, since Evidence and Status are separate axes — and the `Revisit when` triggers on record. An entry can wait in two queues; the count next to *Queues* counts it once. Whether a trigger has fired is a human judgement; the page lists, it does not decide |
| **Timeline** | entries by the month their heading first appeared in Git, stacked by author; superseded events marked below |
| **Authors** | per Git author: created, touched, superseded, first and last activity, the Evidence mix of what they created. Names follow the project's `.mailmap`, as Git's own commands do — two identities of one person are joined there, one line per identity. A name opens the author's profile on the host — asked on the click, in the browser, from the host's API for one of their commits (GitHub, Codeberg / Gitea / Forgejo, Bitbucket); GitLab's API names no account, so there, and whenever the lookup fails, the commit's page opens, which links the author. Not offered with `--anonymize`. Click elsewhere in the row to filter every view |
| **Findings** | the linter's findings, each linked to the entry it sits in |
| **Friends** | a card per friend: its family, if it has one, with the members; where it was read from; which entries here cite it and which of its entries cite this project; the repositories reached by following a thought; the ones that could not be loaded, with the reason |
| **Thoughts** | the numbers — thoughts, evolutions, across projects, going on beyond, the longest — then where many lines lead and where many start, the bridges (entries in the middle of several thoughts), a table by project (starts, passes through, ends), every thought, the evolutions, and the chains going on beyond with *load the whole chains*. Where a chain needs a second look: *Starting from an unconfirmed entry* (the first entry's Evidence is `inferred` or `unknown`) and *Chains through a step in question* (an entry that is open, needs review, waits for confirmation, or is superseded yet still cited by a See — with the later entries, in how many projects, linked after it; the entry itself shows *Linked after this* beside it). A link says two entries are related — often that one follows from the other, not always — so these lists say what to check, not what depends. How it grew: the reader dates every step and draws them on a line; the page lists the lines grown most recently and those resting longest. Pointing at a line or an entry lights it in the graph beside; pointing at a step of a thought anywhere on the page marks it in every graph. The side pane — and its graph — can be made wider from the top of the pane: 1×, 2× (the default), 3×, or half the page, one width where the pane is the graph and one where it holds details (both kept per browser) |
| **Family** | the whole tree the project belongs to, from the root down, each project nested under the one whose `children` block lists it — so a grandchild such as a cluster's dashboard sits under the cluster, seen from anywhere in the tree. Each member with its scope from that routing and how it is available on this machine — a working tree (read and write), a read-only context cache, or not at all, with the clone and cache commands to get it. In an export and in public mode the same tree from the members' published exports; only an export without a `canonical` shows the family as declared in its own config |
| **Projects** | everything this machine knows, from `~/.keep-the-why/projects.json`, the folder next to the project and the personal files — families grouped, a parent with its children indented, each row with its type. *Forget* removes a row from the mapping; for a cache the directory goes too (it is never the only copy of anything), a working tree is never touched. Live server only |
| **This project / family** | the second switch next to the project menu, shown when the project has a family: one setting for the whole page. With *family* every view shows the family merged — overview, topics in the sidebar (a heading per project), entries, authors, queues, timeline, linter findings, the numbers in the strip — with search and graph over the whole tree. A member's topic files and entries keep their project: two `history.md` stay two topics, an entry opens with its own repository's host link, and a topic name in its text resolves in its own project. Remembered per browser; a results-page link carries its own scope. |
| **Local / public** | a switch next to the project menu, shown when the project has a family or a published export. *Local* (the default) reads clones and caches on this machine — the machine the server runs on, whatever device the browser is on. A static page — an export on a docs site, opened on any device — has no such switch: it is published by nature and reads no machine. There the *family* scope works directly, from the members' published exports, fetched only once someone chooses the family. *Public* reads **published exports** instead, starting with this project's own: the browser fetches its `.keep-the-why` as a raw file from its host at `HEAD`, takes the `dashboard-state` line — the URL of its published `state.json` — and loads that, then the members' exports the same way; the page shows the project from its export, with the export's `generated` time next to the switch so nobody mistakes a snapshot for a working tree. Public mode reads what is *published*: a `dashboard-state` line that exists only on an unmerged branch does not count yet, and the page says which file it read and, when a local checkout already carries the line, that it is waiting for a merge. Nothing is cloned, nothing goes through a server of this project's — static files on the member's own pages site; a member without `dashboard-state`, or on a host that refuses the fetch, says so. Family and search work over the fetched exports in the same way; an entry Id is found across them |
| **Entry by Id** | `#entry/<uuid>` opens an entry by its `Id`, in this project or — on the live server — in any other project known here (the page switches to it); an export or a public page looks through the family's published exports instead. Every entry link on the page uses this address, so a copied URL stays valid when a heading is reworded or an entry moves; an old `#entry/<file>#<anchor>` link still opens the entry and the address bar switches to the Id, and an entry without an `Id` keeps the anchor form. The reader shows the entry's `See` references (local ones as links, cross-project ones resolved as the entry is shown — family member or not: on the live server from a checkout or cache on this machine, else from that repository's published export — the one at the repository's top level, so an entry of a project below it (`root`) is not found this way — the row then carries the target's title, status and evidence and links into it; a target without an export, an export without that Id, or one that names another repository as its own, is said so in the row. Foreign text is shown as text, one fetch per repository, no referrer, no credentials, a timeout and a size limit), its `Superseded by` successor and what it supersedes; the details pane has the Id and an "open on the host" link (GitHub, GitLab, Codeberg/Gitea, Bitbucket URL forms — the one place host grammar lives) |
| **Fork checkout** | a dashed *fork of host/owner/repo* pill beside the branch and the repository, linking the repository this checkout was forked from — when the clone has an `upstream` remote (origin is the fork, as `gh repo fork` sets it up), or when `origin` is not the project's `canonical` in `.keep-the-why`; the tooltip says which. No host API is asked — a mirror reads the same as a fork by the second signal. An export made from a fork — the proposal preview before a merge — carries the pill, so the page says whose repository it shows |
| **Status bar** | the two package versions, linking PyPI; when a newer release exists the entry shimmers and its tooltip names the version and the `pip install -U` line |

Search (`/`) takes one or more words, all of which must occur in an entry — its title, body, `Revisit when`, `Source`, `Verification`, `Superseded by`, Id, file, type, status or evidence. The dropdown shows the best hits as you type; **Enter** without a selection opens the results page (`#search/<scope>/<query>`, a link that can be shared): every hit, grouped by project, with its pills, the passage around the match, topic, file, author, dates and Id. Search follows the *this project / family* switch — the family scope covers the **whole tree** the project belongs to, from the root down through every children block (uncles, cousins, a sibling's children), not only the members routing sees; members that are not checked out, cached or published are listed under *Not searched*, never dropped silently. Filters by status, evidence and author apply to every view at once. Keys: `g` graph, `o` overview, `q` queues, `t` timeline, `a` authors, `l` findings.

## The author layer, and its limit

Three Git commands make it: `git blame` on an entry's heading says who committed it and when; `git log -L` on its `Status` line yields the sequence of values with author and date; `git log -S` on the heading finds the commit that introduced it. What Git reports is the committer of record. A coding agent writing inside a developer's session shows up as the developer; a repository where the agent commits under its own identity shows the agent. The dashboard reports what Git says and adds no convention of its own — whether that distinction deserves one is a question for the projects using it, not for the viewer.

## How it is built

- Tested three ways: Python unit tests for everything the server computes (state, Git attribution, mapping, family, forget, export, the endpoints over a real local server); `node --test` unit tests for the page's pure part — `lib.js`, the host URL grammars, tolerant state reading, reference parsing, family grouping — with no dependencies; a jsdom smoke test that loads an export, drives every route and checks that the family view, the entry page by Id, the search and its results page render what they should; and a jsdom test of public mode over a stubbed published tree (root, a sibling in the root's own repository, a child, a member without an export, a repository outside the family reached through a `See`).

- Python, standard library only, with [`keep-the-why-lint`](linting.md) as the parser. The dashboard shows exactly what the linter accepts; entry bodies, cross-references and Git are the only things it adds. A schema change lands in the linter once and the dashboard follows.
- The page is plain JavaScript — two modules, inlined into one page in an export, no framework, no build step, no CDN — so the exported file works offline and the repository carries no second toolchain. The graph is drawn on a canvas by hand, no graph library.
- The server is `http.server` with one background thread for the fingerprint check and a Server-Sent Events endpoint. `--export` inlines the same page with the same state. The page tells live, export and public mode apart and adapts to each — which switches it shows, where it reads a family from, whether it listens for updates — and says which one it is in with a badge in the top bar.
- Its source lives in [`dashboard/`](https://github.com/oliver-zehentleitner/keep-the-why/tree/main/dashboard) of this repository, versioned and published on its own counter like the linter (`dashboard-v<version>` tags). Why it is here and shaped like this is recorded in this project's [`context/`](https://keepthewhy.com/context/).
